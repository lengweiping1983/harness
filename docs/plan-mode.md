# 计划模式：架构、契约与 Codex 对照

计划模式解决的是“先把实施路径交给人审阅，再允许改动”的问题。它与持续 Goal 不同：计划模式是当前对话的只读闸门和一次审批流程，Goal 是跨轮次的完成契约；计划可以帮助说明路径，却不能证明业务目标已经完成。

这份文档把当前 Harness 的计划模式、提示词和可核验边界集中记录下来。源码是行为事实；本文说明如何从源码和事件日志复核行为。比较依据包括本机 Codex 的静态/运行时观察，以及 OpenAI 的公开说明：Codex 的原生计划模式通过 `/plan` 在改动前生成可审阅路径，长程工作依靠“计划、编辑、运行工具、观察、修复、更新状态、重复”的循环，并强调外部化状态与每个里程碑的验证。[OpenAI 长程任务说明](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)；ExecPlan 方案进一步要求计划自包含、可继续、按里程碑验证并记录决定。[OpenAI PLANS.md 方案](https://developers.openai.com/cookbook/articles/codex_exec_plans)。

## 用户可见契约

进入计划模式后，当前会话保持只读探索。用户的“请实现”在此阶段意味着“为实施设计计划”，不意味着可以写文件；用户回答澄清问题也不等于批准。模型必须用 `exit_plan_mode` 提交完整 Markdown 计划，审批卡片只接受批准或要求修改。只有批准成功并退出计划模式，后续回合才可以实施；批准结果会要求先用 `todo_write` 建立执行清单，再使用写工具。

普通文本、模型声称“计划完成”、工具调用成功、计划保存成功和提交 Git 都不等于批准或业务完成。审批通道超时、取消、关闭、参数错误、计划被新版本替换或模式在等待期间改变时，计划保持未批准，当前会话继续受只读约束。

## 与 Goal 的边界

| 能力 | 计划模式 | 持续 Goal |
| --- | --- | --- |
| 作用域 | 当前会话的当前规划阶段 | 线程级、跨轮次的完成契约 |
| 主要状态 | `active`、排队切换、已批准计划版本 | `active`、`paused`、`blocked`、`usage_limited`、`budget_limited`、`complete` |
| 允许动作 | 只读观察、澄清、提交审批 | 按约束实施、验证、继续或诚实停止 |
| 完成证据 | 计划审批回执 | 每条验收标准的业务证据；计划本身不算证据 |
| 退出条件 | `exit_plan_mode` 获批准或用户手动切换 | `update_goal` 通过证据审计，或用户暂停/阻塞/预算停止 |

计划模式可以为 Goal 产生路径，但不能改变 Goal 的状态，也不能把“有计划”升级成 `complete`。批准后的计划版本会注入下一轮上下文，压缩消息表面时仍保留版本与实施进度。

## 状态与事件模型

`harness/app/plan_mode.py` 的 `PlanModeController` 是会话级事实投影。`plan/mode` 事件保存已提交的模式；同一会话最后一条有效事件获胜。回合进行时的用户切换先保存在内存中的 `PlanIntent`，在下一个 step 边界由 `_settle_plan_mode` 提交。提交失败不会清除意图，因此不会把“排队成功”误报成“已切换”。

计划状态与模式状态分开保存。`harness/app/plans.py` 从不可变 `note` 事件折叠版本：`plan_submission` 创建 `pending` 版本，`plan_decision` 写入 `approved`、`revision_requested`、`closed` 或 `superseded`。计划正文、标题、前一版本、提交调用标识和决定反馈都来自事件，不从 UI 草稿或模型普通文本推导。

审批流程由 `harness/tools/builtin/plan_tools.py` 实现：

1. 校验会话、模式、参数类型、一级标题和正文长度；非法参数在写入任何计划事件前失败。
2. 在审阅锁内提交版本并记录当前 review epoch。
3. 通过 `QuestionBroker` 发布带稳定选项 ID 的审批卡片；显示标签可以随语言变化，但决定依据是选项 ID 和无自定义反馈。
4. 用户要求修改时写 `revision_requested`，保留反馈并继续只读；审批通道异常写 `closed`/`plan_review_unavailable`，绝不批准。
5. 重新取得审阅锁，核对版本仍是待审、epoch 未变、模式仍有效且没有父级计划限制；任何一项不满足都关闭旧审阅。
6. 只有所有核对通过才写 `approved`，然后排队退出模式；退出提交和审批决定处于同一把锁保护下。计划事件携带正文 `content_hash`，审批回执和详情以摘要核对确切版本。

模式切换和审批都发布 `plan_mode`、`plan/review` 事件。前端把它们当作投影，不能代替后端事件日志。`PlanProjection.pending` 只表示等待下一个安全边界的意图；当前回合的工具闸门继续按已生效模式限制，避免同一回合前后半段改变权限。

## 工具和权限边界

计划模式拒绝危险工具、需要审批的工具、写文件、写配置、会改变版本库的格式化/生成、提交和执行命令；终端读取也不会绕过这一边界。计划阶段对 `.env`、凭据/令牌文件、私钥和证书容器的 `read`/`glob`/`grep` 引用会被拒绝，安全示例文件仍可读取。只读文件、搜索、静态分析、历史查询、只读浏览器观察和用户澄清可以继续。`exit_plan_mode` 始终注册，即使当前不是计划模式，以保持模式切换时工具目录稳定并避免破坏供应商请求缓存；非计划模式调用会明确失败。

子代理继承父级计划限制。子代理不能批准或退出父会话的计划；父级限制沿真实父链检查，损坏的父链按仍受限处理。并行安全不等于只读，工具的副作用和审批属性仍由注册表闸门判断。

## 提示词契约

提示词资源位于 `harness/i18n/locales/en.json` 与 `harness/i18n/locales/zh-CN.json`，由 `harness/app/plan_mode.py::plan_policy_section` 在请求装配时按当前语言读取。当前策略必须保持以下顺序：

1. 先说明当前模式和不可越过的只读边界。
2. 明确用户确认不等于批准，普通回复不等于提交。
3. 要求通过专用只读工具核对仓库事实，能查明的事实不向用户提问。
4. 要求计划可直接实施，至少包含目标与验收、当前上下文、按子系统的变更、公开 API/schema/数据流、里程碑及每个里程碑的验证、边界与失败恢复、测试、假设、未决风险和停止条件。
5. 规定 `exit_plan_mode` 是本轮最后一个工具调用；计划必须以 Markdown 一级标题开始；审批拒绝后只根据反馈修订并重新提交。
6. 说明审阅通道不可用时停留在计划模式，不能自行实施或退出。

计划提示词只描述路径，不能承诺结果。实施阶段的 `prompt.approved_plan` 只作为上下文参考，始终服从新的用户指令、当前权限和当前计划模式；它明确提醒批准不代表完成。计划工具说明和错误消息均通过双语资源键读取，不能在 Python 中硬编码可见句子。

## 与 Codex/Claude 工作流的比较

Codex 的计划模式和 Harness 的核心安全边界一致：先只读探索、明确的计划提交通道、审批后实施、工具目录稳定、状态外置、完成靠验证。Harness 进一步把计划审批版本、epoch、事件回执和父子限制做成可回查的不变量，因此不会把 UI 卡片关闭或模型文本误判为批准。

Codex 计划模式的实现细节已在本机核实（见 [Codex Agent 内核实测对照](codex-agent-internals.md)）：计划以 `~/.codex/plans/<threadId>/<planId>/PLAN.md` 独立落盘，按线程与计划版本双重标识，因此可跨进程重启恢复且每个版本单独留档；`plan_mode_reasoning_effort` 是独立配置项并可持久化，进入计划模式会切换推理档位；`update_plan`（TODO/清单工具）在计划模式下由工具层直接报错拒绝，而不只是提示词劝导；动作边界的判据是“是否改变仓库跟踪状态”，因此允许跑会写缓存与构建产物的测试和构建，同时禁止改动被跟踪文件，配套判据是“如果这个动作更像在做工作而不是在规划工作，就不要做”；计划输出契约是 `<proposed_plan>` 块，修订时必须整体替换，信息不足以整体替换时先解决疑虑而不产出计划块，且不得在最终输出里问“要不要继续”。模式只能由 developer 消息切换，代码侧还有 `explicit user input can enter Plan mode` 的不可达断言，即用户输入不能进入计划模式被写成不变量。

Harness 的差异在于计划不写独立 Markdown 文件，而是保存在会话事件与投影中并带 `content_hash` 与历史版本；计划模式不切换推理档位；动作边界采用更严格的只读闸门，不区分“仓库跟踪状态”与“构建产物”。放宽到 Codex 的判据需要先有可信的构建产物路径判据，否则会把只读承诺变成不可核对的口头约束。

Codex 长程工作还强调外部化的计划/状态文件、可独立验证的里程碑、失败后修复再继续，以及中途 steer 不清空既有进度。Harness 对应能力由事件日志、计划版本、todo 快照、Goal 证据和回合边界提供；当前计划模式不会自动创建项目级 `PLANS.md`，因为它的计划属于会话审批而非仓库规范。需要仓库级长期执行规范时，应把规范写入项目文档或 `AGENTS.md`，再用 Goal 追踪完成证据。

Claude Code 的 plan mode 同样把探索和实施分开，并通过会话、压缩、后台任务和 hooks 支持长任务。Harness 的差异在于审批决定和工具回执都是本地事件，恢复时不重放未知副作用；代价是重启后不会擅自恢复一个未知是否仍获批准的执行回合，必须重新核对当前计划和外部状态。这是稳定性优先的有意边界，不能写成自动续跑已实现。

## 不虚报与恢复规则

计划提交成功只证明正文已经写入 `plan_submission`；批准只证明用户批准了该版本。实施完成仍必须按 Goal/项目验收逐条核对文件、工具回执、测试或外部结果。发生以下情况时应保留原事件并报告未知或阻塞，不重放写入：

- 审批答案在持久化前连接断开；
- 模式切换排队但尚未经过 step 边界；
- 计划版本被替换或 epoch 已变化；
- 写工具、提交、远端调用或测试结果没有最终回执；
- 压缩、重启或恢复后只能看到计划文本，不能确认原执行副作用。

恢复时先读取事件、计划详情、todo 快照和外部状态，再决定是否继续。任何“工具成功”“回合结束”“提交存在”都必须和业务结果证据分开报告。Goal 的 `complete` 仍需 `checks` 覆盖全部验收标准；计划审批不能填充这些检查。

## 代码入口与针对性验证

- 模式投影、排队切换、父级限制：`harness/app/plan_mode.py`。
- 计划版本与详情、审批决定、实施进度：`harness/app/plans.py`。
- 审批工具与参数/epoch/回执核对：`harness/tools/builtin/plan_tools.py`。
- 循环的 step 边界和收尾反馈：`harness/app/harness.py`、`harness/core/agent.py`。
- 计划双语资源：`harness/i18n/locales/en.json`、`harness/i18n/locales/zh-CN.json`。
- 主要回归：`tests/test_plan_mode_lifecycle.py`、`tests/test_plan_completion.py`、`tests/test_plan_mode_mutation_ownership.py`、`tests/test_prompt_runtime_language.py`。

针对计划模式的最小后端验证应覆盖：只读工具闸门、父子继承、排队切换、审批批准/修改/关闭、epoch 过期、非法正文、回合末结算、双语资源和审批后 todo 建单。前端类型检查不属于本次计划模式文档/后端修改的验收范围；如果环境缺少 `web/node_modules/typescript`，应明确记录而不是用旧产物代替。

## 当前已知边界

本地 REA 对 Codex 原生二进制的 Ghidra 反编译不可用，因此不能声称看到了 Codex 的私有计划实现；可确认的是本机 Goal SQLite 的线程级状态约束，以及官方文档公开的计划/长程工作行为。本文把可观察事实、公开文档和推断分开，避免将推断写成私有实现细节。
