# ChatGPT 普通聊天开发与自动接续

当前方案用于 ChatGPT 网页的普通聊天。ChatGPT 负责理解需求、使用技能、决定代码和原生生图；Harness 负责本机文件、命令、持久状态和验证；浏览器扩展在绑定聊天结束一轮回复后，根据本机实际进展请求下一轮。无需切换到 Work，也不引入另一个付费模型。

开发状态不能只存在聊天上下文中。命令、图片需求、检查点、原请求回执和验证证据由 Harness 保存；扩展只决定何时发送接续消息，不判断代码是否正确。已经受理但结果不明的操作必须回查，不通过重复点击或更换请求号重跑。

## 启动与配对

1. 使用既有 [无模型 MCP 服务](api.md#无模型-mcp-服务)连接普通聊天。先调用 `harness_context`、打开授权项目对话、读取约束和所需技能。需要恢复时，从 `recent_sessions` 找回同一 principal 仍有权访问的最近对话，再用 `harness_session_resume` 读取。
2. 在 Harness 设置的 MCP 页面使用“启动 MCP／停止 MCP”按钮管理主服务。其下方是独立的“普通聊天自动接续”功能块，使用“启用接续／停用接续”按钮，不使用复选框；停用接续不会停止 MCP。启用状态会保存，后续启动 MCP 时自动启动接续桥；MCP 运行时可直接应用启停及端口设置，无需另行双击 CMD。该区域显示扩展应填写的实际地址、配对码遮罩、显隐图标／复制配对码操作，以及项目内扩展目录和版本。配对码由接续桥首次启动自动生成，设置中只读，复制后粘贴到浏览器扩展；未生成时提示启动 MCP，不显示无说明的空白输入框。改端口及重启沿用原配对码，不接受在此输入任意配对码。常规状态不返回完整配对码；完整值仅通过有本机及同源限制的 POST 接口按需读取。接续桥只监听回环地址，不加入公网 MCP 隧道。

   托管桥与 MCP 复用同一份执行器配置，停止 MCP 时回收所属监听。同配置的外部桥经过配对与健康检查后复用，不接管或停止外部进程。其他服务占用端口时接续桥明确失败，不影响 MCP 主服务或杀掉占用者。端口编辑完成后离开输入框即自动保存，无需另点保存按钮；合法范围为 1024～65535 的整数，同值不重复保存，输入法组合过程中不提交。启停按钮只修改启用状态，无效端口草稿不阻止停用；MCP 启停等待已受理的接续配置保存收尾，不重复提交。保存结果未知时只回查状态，保留提示，不自动重放。开发排障仍可使用 `python scripts/start_chat_companion.py --config ... --check`，不作为日常启动步骤。
3. ZIP 需要先解压，不能通过双击 ZIP 安装。交付包根目录直接包含 `manifest.json`，双击其中 `INSTALL.html` 可离线查看中英文安装说明。在 Chrome 的 `chrome://extensions` 或 Edge 的 `edge://extensions` 开启开发者模式，点击“加载已解压的扩展”，选择直接含 `manifest.json` 的文件夹；也可直接加载仓库 `extensions/chatgpt-companion`。在扩展菜单中固定扩展，保留其文件夹，首次安装或更新后刷新目标 ChatGPT 标签页。扩展未发布到应用商店。
4. 打开需要接续的已有普通聊天，点击扩展，填写从 MCP 页面复制的本机地址和配对码，连接后选择开发项目，核对显示的“开启目标”，再点击“开启当前聊天接续”。此时绑定该项目最新的 Harness 会话；同一项目只有一个选择项。开启后绑定固定，不自动跳到其他新会话。重新开启前先停止旧绑定。连接和重新打开弹窗仅执行只读检查，不因此发送消息或重新开启已暂停绑定。
5. 点击“停止自动接续”可停止发起下一条消息；已经受理的消息和本机作业可能继续完成。停止本机命令须另用原作业或流水线控制工具，不把停止扩展等同于撤销写入。

扩展工具栏弹窗使用 760 像素宽度，以两栏显示连接和项目操作，主要控件适配 Chrome 工具栏弹窗的 800×600 上限。右上角“在标签页打开”提供更大操作空间：页面随窗口宽度伸展，内容最大宽度为 1120 像素，640 像素及以下改为单栏。标签页开启接续时仍检查并绑定打开它的原 ChatGPT 标签；原标签已关闭或聊天地址变化时明确拒绝，不能误绑定管理页或其他聊天。未提交的地址、配对码和语言通过独立的一次性浏览器会话存储传递，读取后移除，不放进 URL、不替换后台正在使用的连接设置，也不因此开启接续。长项目目标完整换行，内容超出可见高度时可以滚动。连接步骤、用量限制和检查间隔放在可展开的帮助中，错误和当前接续状态保持可见。

扩展每次开启最长 8 小时，每个绑定最多 100 条发送意图。达到上限后需审查进展再开启。配对码保存在执行器运行根的 `companion-key.json`，扩展设置保存在浏览器本机扩展存储；内容脚本无权读取配对码。当前支持同一台电脑上的 Chrome／Edge 和 `chatgpt.com` 已有聊天地址。

### 连接诊断

| 提示 | 处理 |
|---|---|
| 接续桥不可用 | 启动接续桥并核对本机地址、端口；普通 Harness Web 工作台运行不代表独立 MCP 或接续桥已经运行 |
| 配对码被拒绝 | 从使用同一份执行器配置启动的接续桥重新复制配对码，仅填入扩展 |
| 没有执行器数据库 | 先用同一份配置启动 Harness MCP，不新建空数据库冒充连接成功 |
| 执行器未运行 | 用同一份配置恢复 MCP；已有对话可读取，但后台执行暂时不可用 |
| 没有可访问的开发对话 | 在普通聊天中连接 Harness MCP，调用 `harness_context` 并打开授权项目对话，再重新读取 |
| 扩展无法读取网页 | 安装或更新扩展后先刷新目标聊天；确认在已有聊天标签页中打开扩展 |
| 接续桥响应不匹配 | 核对扩展与接续桥版本；错误回执不能当作已配对或已受理 |

`GET /health` 与其他桥接口一样要求配对凭据和正确 Host，返回固定 `protocol=harness-chat-companion`、`protocol_version=2`、`executor`（`missing`、`invalid`、`offline`、`ready`）及可访问对话数量，不包含配对码、配置路径或对话原文。扩展、托管桥及独立启动入口均核对当前版本，不复用其他版本的监听，也不停止或替换它。更新后需要重启 Harness MCP／接续桥并重新加载扩展。该诊断不创建执行器数据库，也不修改损坏原件。停止按钮在连接和绑定等待期间仍可用；绑定响应迟到不能重新开启已经停止的接续。

浏览器的 `127.0.0.1` 始终指浏览器所在电脑。如果 MCP 在 Mac 或其他电脑，直接填写 Windows 本机地址不会连到远端。可由用户另行配置安全的本地端口转发，把相同的本地端口转发到远端接续桥的回环端口；配对码、执行器配置和运行状态仍以远端为准，须另行联调。当前不提供公网接续桥或自动建立隧道。

## 三层执行分工

| 层 | 职责 | 持久事实 |
|---|---|---|
| ChatGPT 普通聊天 | 技能理解、代码决策、错误诊断、原生生图和视觉审查 | 通过工具保存检查点、图片请求和实际修改 |
| Harness 执行器 | 文件版本检查、后台命令、顺序流水线、验证与验收 | 原请求回执、作业、事件和证据 |
| 浏览器扩展与回环桥 | 观察绑定聊天空闲、根据进展请求接续、核对发送结果 | 发送意图、消息标记和确认状态 |

扩展通过标准 DOM 操作输入框和发送按钮，不读取登录 Cookie，不调用 ChatGPT 私有后端接口，不自动点击审批、登录或验证码。页面控件身份变化时停止，不能用任意按钮或文字猜测替代。不使用扩展时，普通聊天结束后的新推理仍需要用户发送消息。

浏览器定时任务用于重新唤起扩展后台检查；它不能唤醒休眠电脑，也不保证精确准点。见 [Chrome alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms)。内容脚本运行于隔离环境，仍通过共享 DOM 与页面交互，页面结构是需要维护的适配边界；见 [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)。

## 开发与技能

先读取真实源码和项目 `AGENTS.md`，用 `harness_skill_list` 发现技能、`harness_skill_load` 按需加载。技能正文保持原文，返回 `version` 为原始正文 SHA-256。技能提供指令，不扩大本机授权，也不在本机调用模型。

`harness_checkpoint` 使用当前 `expected_revision` 保存摘要和下一步。它是恢复依据之一，不代替原命令、实际文件、失败输出或验证证据。恢复执行事实使用 `harness_session_resume`；只读恢复调用不会产生新开发进展，避免自我触发无限消息。

只有已经确定的步骤才提交 `harness_pipeline_start`。它接受 `session_id`、唯一 `request_id`、最多 30 个 `steps` 及可选 `skills` 名称列表，立即返回 `pipeline_id`。服务存活期间顺序执行，不需要 ChatGPT 为每条命令保持轮询。

| kind | 必填字段 | 可选字段 | 完成依据 |
|---|---|---|---|
| `exec` | `command` | `timeout_ms` | 正常完成、退出码为零、输出无解码错误 |
| `verify` | 已登记的 `verification_id` | 无 | 验证作业完成且当前输入证据通过 |
| `image` | 已登记的 `image_id` | 无 | 真实图片已交付且当前文件摘要匹配 |

不同种类的专用字段不能混用。命令采用执行器操作系统的 Shell 语法；验证采用已登记参数数组。传入 `skills` 时保存技能版本并在每个步骤前核对，变化后停止并要求重新审查。

同一执行器内，活动流水线占用项目，其他命令和文件写入被拒绝；当前对话等待中的指定图片可以交付。该占用不阻止外部编辑器或另一运行根修改项目。流水线复用现有权限、作业、输出、超时和验证机制，不自动提交 Git。

`harness_pipeline_get` 返回步骤、原请求号、作业号、证据和 `next_action`；输出仍用 `harness_job_poll` 读取。完成后，ChatGPT 应审查需求并通过当前验证证据调用 `harness_finalize`。单条命令、流水线或工具成功均不等于业务验收。

## 原生生图与交付

先用 `harness_image_request` 保存原提示词和新文件目标，再将 `image_id` 放入流水线。ChatGPT 原生生图后，调用 `harness_image_deliver` 交付真实文件；成功保存后，等待图片的流水线自动执行后续步骤。

部分普通聊天生图回合可能在生成图片后结束。扩展在绑定聊天中观察到新的、已加载的助手图片后，可以再发送一次交付请求；纯图片回复通过图片资源身份区分，不依赖回复必须包含文字或自身携带消息 ID。未加载的占位图片不作为已生图依据。模型须核对图片与原需求，不能编造下载地址或把图片生成当作已交付。每个进展分别只允许一次生成请求和一次交付请求，失败不自动无限重复生图。

文件参数使用 `openai/fileParams`，由宿主提供 `download_url` 和 `file_id`，以及可选 MIME 和文件名；见 [官方文件输入协议](https://developers.openai.com/plugins/reference#define-file-inputs)。沙箱本地路径、Markdown 地址或文字承诺不能代替可读取的真实文件。执行器校验图片格式、尺寸、字节和摘要，不保存临时下载地址；`delivery_unconfirmed` 保持未知，不自动覆盖。

宠物场景可安排为“等待图片 → 本地切帧 → 帧数、背景及格式验证 → 打包验证”。角色动作、朝向、身体完整性及美术一致性仍需 ChatGPT 查看图片和对应技能验收。解码成功不证明这些语义要求。

## 自动接续与防重发

回环桥以只读方式查看执行器数据库，单独保存浏览器绑定和消息意图，不调用模型或执行项目命令。后台作业运行时等待；已确认失败可请求 ChatGPT 诊断；未知受理结果、取消未确认或损坏记录需人工核实。

扩展每次操作前检查原聊天地址、输入框、草稿、附件、输入法组合、近期用户操作、正在生成状态和对话框。页面连续两次空闲才领取发送意图。普通接续、生图及交付阶段的消息正文都严格为“继续”两个字，不附加指令、会话编号、标记或标点。发送意图的唯一编号只在本机保存；点击后必须观察到新增且正文恰为“继续”的用户消息，历史同文消息不能确认本次发送。原生用户消息按角色标题旁的 `group/user-message` 和 `data-chatgpt-search-message-ids` 边界读取，不把同一回合的回复错误卡片算入用户正文；角色标题与标记为 `data-markdown-copy="exclude"` 的时间等辅助内容同样不计入正文。发送结果不明时暂停并保留意图，不根据历史同文消息或错误卡片自动确认或重发；仅本机已保存的同编号确认回执可在重连后补交。发送未确认先于完成／中断处理，完成后继续的开关不绕过这一保护；已发送“继续”后的回复流失败则属于回复恢复，两者分别判断。

开启接续后，默认在回复结束、已确认的本机任务中断或可恢复的回复错误后，等待页面持续空闲再发送“继续”，直到任务验收完成才停止。“任务完成后仍继续”只控制验收完成后的行为：不勾选时完成即停止，勾选后使用 `next_task` 阶段请求下一个任务；已确认的流水线中断不受此开关影响，始终使用 `resume` 阶段，普通回复使用 `continue`。开关保存为下一次开启的偏好，每个新绑定固定本次选择；修改偏好不重新开启或改写正在运行的绑定。ChatGPT 回复被打断时，页面已将最新回合标记为 `cancelled`，且没有停止／加载控件或弹窗，即可进入连续空闲确认，再发送“继续”；正文尚未开始时以该回合的 `data-turn-key` 建立独立身份，不继承旧回复或旧图片。停止接续须使用扩展的停止按钮，ChatGPT 的停止生成按钮不关闭接续。两种选择均保留 8 小时、100 条发送意图上限，取消本机流水线、未知命令结果、未确认图片交付及未知发送结果仍会暂停，不自动恢复或重放命令。网页尚在生成、显示对话框或无法确认回复结束时继续等待，不将缺少进展本身当成可恢复的中断。

两种选择均按当前助手回复与执行进展共同防重：`GET /state` 可带 `reply_key`，`POST /claim` 必须携带同一个 `reply_key`，值为页面适配器生成的 16 位小写十六进制观察身份。桥将它纳入当前状态的里程碑身份；同一回复和同一进展只发送一次，勾选完成后继续时，即使执行器仍报告上一任务 `complete`，新的空闲回复仍可触发下一次请求。完成里程碑使用最近成功验收事件的序号，后续新的验收不会复用旧身份。图片等待状态不按回复拆分生成／交付里程碑，保留每次图片进展的一次生成和一次交付；生成消息已确认后，若 ChatGPT 回复被取消，可用 `resume` 发送恢复消息，按当前图片进展与取消回复的 `reply_key` 单独防重，不重复领取 `generate`。领取阶段只接受对应状态：`continue` → `continue`，`image` → `generate`／`deliver`／有回复身份且生成消息已确认的 `resume`，`complete` → `next_task`，`interrupted` → `resume`。未确认发送在整个绑定内阻止新领取，不能靠更换回复身份绕过；消息插入前及提交前仍核对原回复身份、取消状态和生成控件。上述桥协议不改变执行器数据库结构，也不重写既有发送记录。

后台使用单次浏览器 alarm，开启时立即检查一次，此后每次检查结束都在 120～180 秒之间重新随机取整数秒，安排下一次检查；后台重新唤起时保留已安排的单次 alarm，缺失或仍为周期 alarm 时重新安排。连续空闲观察至少相隔 3 秒。回复结束且满足接续条件时，通常在后续一到两次检查中接续（约 2～6 分钟）；浏览器休眠和调度延迟可能更久，这不是发送时限保证。忙碌、草稿或作业执行状态会重置连续空闲窗口。弹窗分别显示本机作业、页面回复、未识别回复及空闲确认状态，并展示上次检查时间；“未识别到助手回复”不能解释成“本机任务仍在运行”。

绑定针对开启时确认的项目和 Harness 开发会话，不会自动追随其他新会话。聊天中的开发目标切换并另开 Harness 会话后，需要停止接续、重新连接读取项目的最新会话，再重新开启。图片任务须先登记 `harness_image_request`；仅在聊天生成图片，不能形成执行器的图片等待和交付状态。

本机新检查点、修改、作业终态及流水线推进可以形成新的执行进展；只读查询和重复空闲检查不会形成新进展。无论是否勾选完成后继续，新助手回复都可形成新的接续机会；因此同一执行进展后的连续回复中断或错误仍可恢复，不因重复检查同一回复而再次发送。

| 情况 | 当前处理 |
|---|---|
| 聊天结束回复，确定性命令仍运行 | 本机继续，扩展等待 |
| 后台完成且页面空闲 | 保存意图后发送“继续” |
| 验收完成 | 默认停止；勾选完成后继续时，在页面空闲后发送“继续” |
| 已确认任务中断、回复取消或可恢复的回复错误 | 无需勾选，页面持续空闲后发送“继续”，直到验收完成 |
| 图片生成后回合结束 | 新助手图片可触发一次“继续”，交付事实仍由执行器核对 |
| 用户输入、组合输入或有附件 | 保留草稿并等待 |
| 标签页换到其他聊天、关闭或控件变化 | 停止接续，保留原绑定和回执 |
| 消息点击后确认未收到 | 暂停并查询原消息，不自动重发 |
| 回环桥暂时不可达 | 继续只读连接检查，不重发消息 |
| MCP 服务重启 | 保存状态可恢复；确认作业按原回执核对，未知副作用不重放 |
| 本机关闭、休眠、浏览器关闭或额度耗尽 | 不能承诺持续运行；恢复后核对原状态 |

`harness_request_get` 按原工具名和请求号返回 `not_found`、`running`、`outcome_unknown` 或 `finished`。仅 `finished` 有确认回执；`not_found` 不是重放授权。`harness_pipeline_control` 使用当前修订继续或取消；受理结果或进程清理不明时保持中断，不声称已经停止。

## 验证与适用边界

`tests/test_execution_pipeline.py` 使用隔离项目、真实进程、图片字节与持久回执核对顺序执行、验证、交接、重启、取消及未知结果保护。`tests/test_chat_companion.py` 核对回环桥绑定、配对、只读状态和发送意图；浏览器回归使用受控聊天 DOM 验证草稿、附件、输入法、错误聊天、消息确认及控件变化。统一交付入口见 [开发与测试](development.md)。

使用 `python scripts/package_chat_companion.py --output /absolute/path/Harness-Chat-Companion.zip` 生成交付包。打包入口仅收集明确的扩展资源，从双语资源生成离线安装说明，并保存逐文件 SHA-256；不收集运行数据、配对码或仓库其他内容。真实扩展回归加载的是该 ZIP 解压后的根目录，覆盖配对失败、连接恢复、绑定迟到后的停止及语言往返；页面与后台回归另核对纯图片身份及一次生成、一次交付。打包测试核对清单、摘要、源文件字节与确定性输出。

这些回归不等同于在用户登录的 ChatGPT 上验收。当前页面适配、原生生图后的文件参数可用性、MCP 刷新和审批策略、断线重连、长时间账号额度仍需实际客户端验证。扩展不会自动批准工具或绕过站点限制；这些限制可能要求人工处理。

当前页面适配器识别登录态 `form[data-chatgpt-composer]` 中无 ID 的唯一可见 `contenteditable[role=textbox]`，输入后等待动态出现的同表单提交按钮；同时保留 `#mobile-composer-prompt`、`#prompt-textarea` 和显式 composer 容器分支。隐藏 composer 不计为第二个输入框。发送前再次核对同一输入框及容器身份、附件、忙碌标记和对话地址。消息识别同时支持旧版 `data-message-author-role` 和登录态 `[data-turn-key]` 中的 `h4[data-conversation-role]`，只读取同角色消息区域，不把标题本身当作完整回复或把用户图片当作助手图片；接续始终接受 `complete`、已标记的 `cancelled` 和下述可重试回复错误进入空闲确认，不受完成后继续开关影响；未识别的状态保持等待。停止、加载控件或弹窗仍优先阻止发送。

两种选择均识别当前回复的可重试错误：错误卡片须在同一 `main` 中、当前回合内或其后、输入框之前，为带错误表面样式的可见 `aside[role=alert]`，且仅有一个可见的“重试／Retry”按钮。停止／加载标记、弹窗、禁用或 `aria-disabled` 的重试按钮仍阻止发送；更早回合的错误、输入框内提示以及“新建聊天／切换默认模型”等其他动作不据此开放接续。扩展只发送新的恢复消息，不点击原生重试按钮；同一回复身份与进展仍按桥的持久意图防重。

方案把长期执行和恢复事实移到本机，把普通聊天结束后的接续交给显式开启的扩展。它减少人工发送“继续”，并为未知结果提供可核对的停止状态；不保证网页结构永远不变或无限无人值守。
