# 文本编码

Harness 自有源码及资源使用不带 BOM 的 UTF-8；运行时文本默认 UTF-8，其他编码必须明确指定。Unicode 字符数、文本编码、文件换行是独立概念。

## 默认入口

独立开发、验证与测试发现入口通过 `scripts/python_bootstrap.py` 在执行工作前进入 UTF-8 解释器模式，并显式配置标准流。未启用时使用受等待的所属子解释器，保留业务参数和退出码；只替换解释器选项区内精确的 `utf8` 开关，无关 `-X`／`-W` 选项及执行目标后的参数保持原文和顺序。继承的 `PYTHONUTF8=0` 或 `-X utf8=0` 不改变该默认，不在已接受写入后重启。macOS 的 `scripts/dev.command` 直接以 `-X utf8` 启动热更新监督进程，避免增加一层启动等待。

桌面源码/安装包后端与浏览器测试共享 Python 环境构造。Windows 命令的标准库桥接进程先在所属私有控制台设置 UTF-8，再启动实际 cmd；命令正文只由实际 cmd 解析一次，避免代码页启动缓存及嵌套 Shell 破坏引号。钩子和终端管道回退复用该初始化，不修改用户控制台。运行库子进程使用 `utf8_env`，只返回新的环境映射，不修改调用方环境。ACP/MCP 的 `stdio_env` 先清洗宿主 IDE 标志并合并显式环境，再固定 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`；这两个字段不能被额外环境改回其他编码，其他显式覆盖仍保留。CLI 主入口配置标准流；SDK 导入不设置环境、不重配标准流、不修改内置 `open`。运行库自有文件、配置和生成器仍显式声明编码，因此不依赖嵌入宿主是否启用 UTF-8。

## 输出编码接口

`bash`、`pwsh`、`run_code`、`harness_exec` 接受可选 `output_encoding`，省略时为 `utf-8`。名称最长 128 字符，通过 Python 文本编解码器登记校验并返回规范编码名；未知值、空白文本、超长名称、非字符串及非文本编解码器在启动前拒绝。此参数声明输出字节的编码，不会强迫任意第三方程序改变输出格式。

后台作业在创建/前台超时交接时继承编码，后续读取不得切换；前台预览、最终结果和后台输出复用严格增量解码。`encoding_errors` 包含 `channel`、`encoding`、`offset`（从通道开始计数的字节偏移）与原始 `reason`。错误发生后只保留此前合法文本，继续排空输出并等待原执行收尾；真实退出码不变，不自动重跑。输出不完整不能作为验收成功证据。

bash 与 pwsh 的正常退出结果由 `tools/command_output.py:exited_command_result` 统一装配，保留原退出码、输出摘要、日志引用和解码错误；退出码为零但解码不完整时仍标记错误。PowerShell 的 CLIXML 处理及各工具的超时、后台交接仍由原执行器处理。

终端工具、服务 SDK 和创建 HTTP 请求同样接受 `output_encoding`，创建后固定。POSIX 字节终端支持显式编码；Windows ConPTY 本身为 Unicode 传输，适配器输出固定 UTF-8，因此在启动前拒绝其他编码，不能把 Unicode 再误按 GBK 解码。终端/作业/实时输出界面单独显示编码错误，不冒充进程失败或自行关闭终端。

普通文件读写工具保持严格 UTF-8，不增加 GBK 编辑或自动转码。确有外部格式转换需求时，由调用方显式使用该格式的工具或转换脚本处理；读取失败保留文件原件。

账号授权及模型目录的JSON响应、HTTP错误分类正文和JWT载荷在JSON解析前严格解码UTF-8，不让JSON字节解析自动接受UTF-16/32。拒绝仍使用现有双语安全分类，保留HTTP状态，不回显授权材料、不重放请求；JWT载荷解析失败返回空声明，不作为身份校验。

## 具名适配例外

| 边界 | 处理依据 | 回归 |
|---|---|---|
| PowerShell `EncodedCommand` | 参数协议要求 UTF-16LE 的 Base64，保留原有包装及行号处理 | PowerShell 启动/收尾及 UTF-8 专项 |
| PowerShell CLIXML | 错误序列化协议按 UTF-8 解包，不受原生命令 output_encoding 改写 | PowerShell 及编码专项 |
| Windows 凭据存储 | 现有 `CredentialBlob` 使用 UTF-16LE；这是已有数据表示，不进行隐式迁移 | 凭据完整性及连接器回归 |
| 智能体/Skill 文本导入 | 既有适配器明确接受 UTF-8 BOM；不扩大到运行配置或新源码 | 智能体/Skill 解析回归 |
| HTTP 外部网页 | 使用响应明确声明的 charset；未声明时 UTF-8，不再猜测 GBK | 网页工具及编码专项 |
| HTTP 下载文件名 | ASCII 回退名用于协议头，原始名称以 `filename*=UTF-8` 传递；ASCII 适配不属于正文解码 | 响应编码回归 |
| Windows 用户 SID | 从原始输出提取 ASCII SID，不按未知本地用户名编码解码整行 | MCP 服务权限及 Windows 分支 |
| 已知字节截断的预览 | 严格增量解码只允许末尾半字符尚未完成；正文内非法字节仍拒绝 | 文件前缀、差异及编码专项 |

## 验证

`python scripts/check_text_encoding.py` 扫描版本控制及新增自有文本，严格检查 UTF-8、BOM 和运行库/生成器的隐式文本 I/O；排除任意 `research/` 目录，不扫描用户数据、依赖或构建产物。可用 `--report output/utf8-file-audit.json` 输出逐文件散列及检查记录。测试文件由统一解释器入口控制默认；不能用环境默认替代 SDK 文件边界的显式规则。

编码检查已接入统一验证和 CI。专项覆盖 UTF-8/GBK/UTF-16、多字节分块、非法及末尾残缺字节、真实进程退出、一次执行、宿主隔离和关闭 UTF-8 默认的入口。工具可输出可删除的 JSON 回执；长期编码边界及防回归依据保留在本文与对应源码测试中。
