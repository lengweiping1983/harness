# 实验评估室

面向实验设计、产品效果评估、A/B与基准结果复核。先明确需要支持什么决策，再按资料与约束选择测量、设计和推断审阅视角；不是每次都跑完整实验流程，也不自动开展真实实验。

在仓库根目录执行 `.venv/bin/python scripts/install_example_teams.py --scenario experiment-lab` 预览，加 `--apply` 安装。也可在 Agent 页面安装三个成员目录，再安装 `experiment-lab-evaluation` 团队。在会话选择器选择「实验评估室」，正常发送需求。

示例输入：

> 阅读现有实验报告，核对主张与数据是否匹配。先让 measurement 和 skeptic 分别复核测量口径及推断边界，再汇总能确定的描述量、竞争解释和最重要的补证据；本次不要完整实验方案。

需要新实验时，可要求 design 参与设计比较、分配/分析单位及观测方案。只探索假设时保留不同解释，不强迫显著性检验、精确样本量或唯一结论。角色和方法由本次提示控制。

团队主理人与成员均只读，不执行命令、不改数据或部署、不招募、不操作账户和真实用户流量。样本量、阈值和统计结论必须有本题输入与设计依据；没有执行过的实验不能写成测得效果。独立成员不是独立数据来源，意见一致不构成因果证据。安装及工程检查仅证明定义可用，真实判断能力需要另外验证。

## 固定推断回归

显式运行 `.venv/bin/python scripts/evaluate_research_team.py --run --case tests/fixtures/experiment_inference`，输出 evaluation.json 路径后，用同一命令的 `--collect <evaluation.json路径> --case tests/fixtures/experiment_inference` 收集原运行，不重复提交。案例同时检查可支持算术、明确否证和缺证主张，包括“取证日志现成且成本最低”这一缺证断言；期望答案不复制到模型工作目录。

评分核对分类、字面引用、源文件哈希和本次成功完成的真实成员来源。它不自动证明 reason 的完整语义支持，案例可显式设置 `member_read_paths`，要求本次直接成员仅调用 read 读取列出的资料文件；此时收集器按持久轨迹核对调用及参数，未知归属、上下文缺失、参数截断或分页不完整均不判通过。它不证明工具实际访问目标、历史符号链接或所有资料来源，完整理由仍需原文与轨迹审阅。它不测开放任务的全部判断或稳定性，也不代表世界排名。案例要求的 JSON、成员与读取范围只适用于该次评测，不是团队默认工作流。
