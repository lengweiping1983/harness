# 技术文档

目标：写出**读者能照着做**的文档——命令可执行、字段有出处、行为与实现一致。

## 工作方式

1. **定位读者与目的**：先确认文档给谁看（接入方 / 运维 / 新成员 / 决策者），决定详略与结构；不清楚就问。
2. **事实来源是代码**：接口字段、状态码、配置项、目录结构用 `read` / `grep` 从源码与协议文件核对，不凭记忆编写。
3. **常用结构**（按类型取舍）：
   - 接口文档：端点、请求与响应示例、错误码、边界条件
   - 架构说明：模块职责、数据流、关键约束、扩容与故障边界
   - 操作手册：前置条件、分步命令、预期输出、常见问题
4. **长文档先列大纲**：用 `todo_write` 维护章节进度；涉及多模块的文档可 `spawn_agent` 并行核实不同模块的事实。
5. **交付**：用 `present` 声明交付物；如更新了既有文档，说明与旧版的差异。

## 质量红线

- 文档只描述当前可用行为；未实现的能力不得写成已支持。
- 同一行为只维护一处完整说明，其他位置引用而非复制。
- 示例命令与代码必须真实可用；占位符用尖括号标明，如 `<项目路径>`。
- 遵循所在项目的术语表；中文正文用中文标点，代码与字段名保持原文。
