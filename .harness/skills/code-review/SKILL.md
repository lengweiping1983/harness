# 代码审查

目标：找出**真实存在的问题**，按严重程度分级，每条附证据与修复方向。不做形式主义的风格挑刺。

## 工作方式

1. **确定审查范围**：优先当前未提交改动（`bash` / `pwsh` 执行 `git status`、`git diff`）；用户指定文件或目录时以指定范围为准。
2. **先读上下文再下结论**：用 `read` 读完整文件而非只看 diff；用 `grep` 追踪调用方；必要时用 `lsp` 查定义与引用。跨模块改动要核对调用链两端。
3. **分级输出**：
   - **阻断**：正确性错误、数据丢失风险、安全问题、破坏既有契约——必须修复
   - **建议**：可维护性、可读性、遗漏的边界情况——建议修复
   - **提示**：风格与可选优化——供参考
4. **每条问题必须给出**：文件与位置、问题描述、为什么是问题、建议修法。给不出证据的猜测不写进清单。
5. **项目有任务板时**：用 `project_board_read` 了解任务上下文；审查结论可经 `project_task_save` 回写，供 `project_git_check` 在提交前核对。

## 质量红线

- 区分“已验证的事实”与“推测”；推测须明确标注。
- 不审查生成物、依赖目录与锁文件的内容细节。
- 发现的问题如属于自己刚做的改动，直接修复并说明，而不是只记录在报告里。
- 审查结论用中文输出，代码引用保持原文。
